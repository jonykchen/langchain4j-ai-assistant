## 1. 架构差异：一切语法的根源

很多语法差异不是"随便设计的"，而是底层架构不同导致的。理解这一点，差异就不需要背。

### 1.1 进程模型

```
MySQL（线程模型）                    PostgreSQL（进程模型）
┌──────────────┐                  ┌──────────────┐
│  客户端连接1   │                  │  客户端连接1   │
│  ┌──────────┐│                  │  ┌──────────┐│
│  │ Thread 1 ││                  │  │ Process 1││
│  └──────────┘│                  │  └──────────┘│
│  客户端连接2   │                  │  客户端连接2   │
│  ┌──────────┐│                  │  ┌──────────┐│
│  │ Thread 2 ││                  │  │ Process 2││
│  └──────────┘│                  │  └──────────┘│
│  共享内存缓冲池 │                  │  共享内存缓冲池 │
└──────────────┘                  └──────────────┘
```

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| 连接处理 | 每连接一个线程 | 每连接一个进程 |
| 内存隔离 | 线程共享地址空间，隔离性弱 | 进程独立地址空间，隔离性强 |
| 崩溃影响 | 一个线程崩溃可能拖垮整个服务 | 一个进程崩溃不影响其他进程 |
| 上下文切换 | 线程切换快 | 进程切换开销更大 |

**语法影响：** PostgreSQL 的 `pg_terminate_backend(pid)` 杀连接就是杀进程；MySQL 的 `KILL CONNECTION id` 是终止线程。

### 1.2 存储引擎

```
MySQL：可插拔存储引擎
┌─────────────────────────────────┐
│           SQL 层（Server）        │
├────────┬────────┬───────────────┤
│ InnoDB │ MyISAM │  Memory ...   │   ← 不同引擎特性不同
└────────┴────────┴───────────────┘

PostgreSQL：统一存储引擎
┌─────────────────────────────────┐
│           SQL 层（Server）        │
├─────────────────────────────────┤
│        统一存储引擎               │   ← 行为一致、可预测
└─────────────────────────────────┘
```

**原理差异的影响：**
- MySQL 不同引擎行为不一致（MyISAM 不支持事务，InnoDB 支持），导致语法上有引擎限定
- PostgreSQL 行为一致，没有 `ENGINE=InnoDB` 这类语法
- MySQL 的 `SHOW TABLE STATUS` 需要区分引擎信息，PostgreSQL 不需要

### 1.3 MVCC 实现差异

这是理解两者行为差异的**核心原理**。

```
MySQL InnoDB MVCC                  PostgreSQL MVCC
─────────────────                  ────────────────
回滚段（Undo Log）                  行多版本（Tuple）

┌─────────┐                        ┌──────────────┐
│ 最新数据  │ ← 直接在数据页         │ Tuple 3 (当前) │ ← 新版本
│          │                        │ Tuple 2 (旧)   │ ← 旧版本还在
│ Undo Log │ ← 旧版本在这里         │ Tuple 1 (更旧) │ ← 更旧版本
└─────────┘                        └──────────────┘
旧版本在 Undo Log 中                旧版本就在数据页中
需要回溯 Undo Log 构建              直接可见，无需回溯
```

| 维度 | MySQL (Undo Log) | PostgreSQL (多版本 Tuple) |
|------|------------------|--------------------------|
| 读旧版本 | 需要回溯 Undo Log 重建 | 数据页直接有旧版本 |
| 读性能 | 长事务需回溯多条 Undo | 直接读对应版本，更快 |
| 空间回收 | Undo Log 可及时清理 | 旧版本需 VACUUM 清理 |
| 写冲突 | 快照读不阻塞，当前读可能阻塞 | 读写完全不阻塞 |

**语法影响：**
- PostgreSQL 需要 `VACUUM` 命令清理死元组，MySQL 不需要
- PostgreSQL 的 `UPDATE` 实际是 DELETE + INSERT（新版本），MySQL 是原地更新
- PostgreSQL 大量更新后表膨胀是常见问题，需要 `VACUUM FULL` 或 `pg_repack`

## 2. 类型系统差异

### 2.1 类型严格程度

**原理：** PostgreSQL 有严格的类型系统，不同类型之间不会隐式转换；MySQL 设计哲学是"尽量让查询跑起来"，做了大量隐式转换。

```sql
-- MySQL：隐式转换，不报错
SELECT 1 + '1';           -- 结果：2（字符串自动转数字）
SELECT * FROM t WHERE int_col = '1';  -- 字符串自动转整数
SELECT * FROM t WHERE varchar_col = 1; -- 整数自动转字符串

-- PostgreSQL：严格类型，可能报错
SELECT 1 + '1';           -- 报错！需要 SELECT 1 + '1'::INT
SELECT * FROM t WHERE int_col = '1';  -- 某些场景报错，需要显式转换
```

**为什么 PostgreSQL 更严格？**
- 隐式转换可能导致索引失效（MySQL 中 `varchar_col = 1` 会全表扫描）
- 隐式转换有歧义（`'1' + 0` 是数值加法还是字符串拼接？）
- 严格类型让你在开发阶段就发现错误，而非上线后出问题

### 2.2 数值类型

```sql
-- MySQL 自增
id INT AUTO_INCREMENT PRIMARY KEY

-- PostgreSQL 自增（三种方式）
id SERIAL PRIMARY KEY           -- 等价于：INTEGER + 自动创建序列
id BIGSERIAL PRIMARY KEY        -- 等价于：BIGINT + 自动创建序列

-- PostgreSQL 10+ 推荐方式（SQL 标准）
id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

**原理：**

| 方式 | MySQL AUTO_INCREMENT | PG SERIAL | PG IDENTITY |
|------|---------------------|-----------|-------------|
| 底层实现 | 表属性，引擎内维护 | 独立 Sequence 对象 | 独立 Sequence 对象 |
| 可否手动插入 | 需设置 `NO_AUTO_VALUE_ON_ZERO` | 可以，`DEFAULT` 时自动 | ALWAYS 禁止手动，BY DEFAULT 允许 |
| 重置计数器 | `ALTER TABLE t AUTO_INCREMENT = 1` | `ALTER SEQUENCE RESTART WITH 1` | 同左 |
| 跨表共享 | 不支持 | 多列共享同一 Sequence | 同左 |

**SERIAL 的问题：** 可以被手动插入值，可能导致序列与实际数据不同步。IDENTITY 列修复了这个问题。

### 2.3 布尔类型

```sql
-- MySQL：没有真正的 BOOLEAN
is_active TINYINT(1) DEFAULT 1
SELECT * FROM users WHERE is_active = 1;       -- 数字比较
SELECT * FROM users WHERE is_active = TRUE;     -- TRUE 只是 1 的别名

-- PostgreSQL：原生 BOOLEAN
is_active BOOLEAN DEFAULT TRUE
SELECT * FROM users WHERE is_active = TRUE;
SELECT * FROM users WHERE is_active;             -- 简写，更简洁
SELECT * FROM users WHERE is_active IS NOT FALSE; -- 三值逻辑
```

**原理：** PostgreSQL 实现了 SQL 标准的三值逻辑（TRUE / FALSE / NULL），MySQL 用 TINYINT 模拟，只有 0 和非 0。

```sql
-- 三值逻辑的影响
SELECT NULL = TRUE;    -- PostgreSQL: NULL（不是 FALSE）
SELECT NULL = FALSE;   -- PostgreSQL: NULL（不是 TRUE）
SELECT NULL IS NULL;   -- PostgreSQL: TRUE

-- MySQL
SELECT NULL = TRUE;    -- MySQL: NULL
SELECT NULL = FALSE;   -- MySQL: NULL
-- 行为一致，但底层类型不同导致函数行为不同
```

## 3. 字符串与标识符

### 3.1 引号规则

```sql
-- MySQL：单引号和双引号都当字符串
SELECT 'hello';          -- 字符串
SELECT "hello";          -- 也是字符串（默认模式）
SELECT `name` FROM `user`;  -- 反引号用于标识符

-- PostgreSQL：严格区分
SELECT 'hello';          -- 字符串常量
SELECT "hello";          -- 标识符（列名、表名）
SELECT name FROM "user"; -- "user" 是标识符（避免与保留字冲突）
```

**原理：** PostgreSQL 遵循 SQL 标准——单引号包裹字符串常量，双引号包裹标识符。MySQL 默认不区分，但设置 `ANSI_QUOTES` 模式后行为与 PostgreSQL 一致。

**实际影响：**

```sql
-- 这条 SQL 在 MySQL 能跑，在 PostgreSQL 报错
SELECT status, "status" FROM users;
-- MySQL：两列都是 users.status 的值
-- PostgreSQL：第二列是名为 "status" 的列（没问题），但如果写 SELECT "active" 则是找名为 active 的列

-- 从 MySQL 迁移到 PostgreSQL 最常见的报错
INSERT INTO users (name) VALUES ("Tom");
-- PostgreSQL 报错：column "Tom" does not exist
-- 正确写法：
INSERT INTO users (name) VALUES ('Tom');
```

### 3.2 E-escape 字符串

```sql
-- PostgreSQL 特有：E'' 转义字符串
SELECT E'Hello\nWorld';    -- \n 被解释为换行
SELECT 'Hello\nWorld';     -- \n 只是普通字符（标准字符串）

-- MySQL：默认支持转义
SELECT 'Hello\nWorld';     -- \n 就是换行
```

**原理：** PostgreSQL 默认遵守 SQL 标准，普通字符串中 `\` 不作为转义符。需要转义时用 `E''` 前缀。这避免了一个常见坑：路径 `C:\new\folder` 在 MySQL 中 `\n` 会被转义。

## 4. 自增主键

```sql
-- MySQL
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50)
);

-- 插入时不指定 id
INSERT INTO users (name) VALUES ('Tom');  -- id = 1

-- 手动指定 id
INSERT INTO users (id, name) VALUES (100, 'Jerry');  -- 可以

-- 重置自增
ALTER TABLE users AUTO_INCREMENT = 1;
```

```sql
-- PostgreSQL
CREATE TABLE users (
    id SERIAL PRIMARY KEY,    -- 底层创建了序列 users_id_seq
    name VARCHAR(50)
);

-- 插入时不指定 id
INSERT INTO users (name) VALUES ('Tom');  -- id = 1

-- 手动指定 id（小心！序列不会自动推进）
INSERT INTO users (id, name) VALUES (100, 'Jerry');  -- 可以，但序列还停在 2

-- 下一条自动插入会冲突！
INSERT INTO users (name) VALUES ('Lucy');  -- id = 2，但 2 已存在？不，是序列值
-- 解决：重置序列
SELECT setval('users_id_seq', (SELECT MAX(id) FROM users));
```

**原理对比：**

| 维度 | MySQL AUTO_INCREMENT | PostgreSQL SERIAL |
|------|---------------------|-------------------|
| 存储位置 | 表元数据中 | 独立的 Sequence 对象 |
| 手动插入后 | 自增值 = MAX(id) + 1 | 自增值 = 序列当前值 + 1（不感知手动插入） |
| 重置 | `ALTER TABLE ... AUTO_INCREMENT` | `ALTER SEQUENCE ... RESTART` 或 `setval()` |
| 多列自增 | 不支持 | 支持多列各自独立序列 |
| 共享序列 | 不支持 | 多表可共享同一序列 |

**迁移注意：** 如果从 MySQL 迁移，且有手动插入 id 的逻辑，迁移到 PostgreSQL 后必须 `setval()` 同步序列值。

## 5. 时间函数与日期处理

### 5.1 核心差异

**原理：** MySQL 的时间函数是自有体系；PostgreSQL 的时间函数更接近 SQL 标准，同时提供了大量扩展函数。

```sql
-- 当前时间
MySQL:    NOW()                          -- 返回 DATETIME
PG:       NOW()                          -- 返回 TIMESTAMPTZ
          CURRENT_TIMESTAMP              -- 等价于 NOW()
          CLOCK_TIMESTAMP()              -- 每次调用返回真实当前时间（非语句开始时间）

-- 区别：NOW() 在 PG 中返回事务开始时间，CLOCK_TIMESTAMP() 返回真实时间
SELECT NOW(), CLOCK_TIMESTAMP();  -- 同一事务中多次调用，NOW() 不变，CLOCK_TIMESTAMP() 变化
```

### 5.2 日期格式化

```sql
-- MySQL
SELECT DATE_FORMAT(NOW(), '%Y-%m-%d %H:%i:%s');   -- 2024-04-20 14:30:00
SELECT DATE_FORMAT(NOW(), '%Y年%m月%d日');          -- 2024年04月20日

-- PostgreSQL
SELECT TO_CHAR(NOW(), 'YYYY-MM-DD HH24:MI:SS');   -- 2024-04-20 14:30:00
SELECT TO_CHAR(NOW(), 'YYYY年MM月DD日');            -- 2024年04月20日
```

**格式符映射：**

| 含义 | MySQL | PostgreSQL |
|------|-------|-----------|
| 年(4位) | `%Y` | `YYYY` |
| 月(2位) | `%m` | `MM` |
| 日(2位) | `%d` | `DD` |
| 时(24) | `%H` | `HH24` |
| 时(12) | `%h` | `HH12` |
| 分 | `%i` | `MI` |
| 秒 | `%s` | `SS` |
| 星期名 | `%W` | `Day` |
| 月名 | `%M` | `Month` |

### 5.3 日期加减

```sql
-- MySQL
SELECT DATE_ADD(NOW(), INTERVAL 7 DAY);
SELECT DATE_SUB(NOW(), INTERVAL 1 MONTH);
SELECT NOW() + INTERVAL 1 HOUR;

-- PostgreSQL
SELECT NOW() + INTERVAL '7 days';
SELECT NOW() - INTERVAL '1 month';
SELECT NOW() + INTERVAL '1 hour';
```

**原理：** PostgreSQL 的 `INTERVAL '7 days'` 是一个完整的间隔类型，支持更复杂的写法：

```sql
SELECT NOW() + INTERVAL '1 year 2 months 3 days 4 hours 5 minutes 6 seconds';
-- MySQL 需要多次 DATE_ADD 嵌套
```

### 5.4 日期截断

```sql
-- MySQL：用 DATE_FORMAT 模拟
SELECT DATE_FORMAT(NOW(), '%Y-%m-01');            -- 月初
SELECT DATE_FORMAT(NOW(), '%Y-01-01');            -- 年初

-- PostgreSQL：DATE_TRUNC 更优雅
SELECT DATE_TRUNC('month', NOW());                -- 月初 2024-04-01 00:00:00
SELECT DATE_TRUNC('year', NOW());                 -- 年初 2024-01-01 00:00:00
SELECT DATE_TRUNC('day', NOW());                  -- 当天零点
SELECT DATE_TRUNC('week', NOW());                 -- 本周一
SELECT DATE_TRUNC('quarter', NOW());              -- 本季度初
```

**原理：** `DATE_TRUNC` 是对时间轴的"向下取整"。PostgreSQL 把时间理解为连续的时间轴，截断就是找到当前粒度所在周期的起点。MySQL 没有这个概念，需要用格式化函数模拟。

### 5.5 实战：查询本月数据

```sql
-- MySQL
SELECT * FROM token_usage_logs
WHERE DATE_FORMAT(request_time, '%Y-%m') = DATE_FORMAT(NOW(), '%Y-%m');

-- 更好的 MySQL 写法（走索引）
SELECT * FROM token_usage_logs
WHERE request_time >= DATE_FORMAT(NOW(), '%Y-%m-01')
  AND request_time <  DATE_ADD(DATE_FORMAT(NOW(), '%Y-%m-01'), INTERVAL 1 MONTH);

-- PostgreSQL
SELECT * FROM token_usage_logs
WHERE request_time >= DATE_TRUNC('month', CURRENT_DATE)
  AND request_time <  DATE_TRUNC('month', CURRENT_DATE) + INTERVAL '1 month';
```

## 6. 类型转换

```sql
-- MySQL：隐式转换 + CAST
SELECT CAST('123' AS SIGNED);        -- 字符串转整数
SELECT CAST('3.14' AS DECIMAL);      -- 字符串转小数
SELECT '123' + 0;                    -- 隐式转换为数字

-- PostgreSQL：CAST + :: 简写
SELECT CAST('123' AS INTEGER);       -- 标准写法
SELECT '123'::INTEGER;               -- PostgreSQL 简写（最常用）
SELECT '123'::INT;                   -- INTEGER 缩写
SELECT '2024-01-01'::DATE;           -- 字符串转日期
SELECT '[1,2,3]'::JSONB;             -- 字符串转 JSONB
SELECT '0.1 0.2 0.3'::VECTOR(3);    -- 字符串转向量
```

**原理：** `::` 是 PostgreSQL 的历史语法，源自 PostgreSQL 的前身 POSTGRES。它比 `CAST()` 更简洁，在日常使用中更常见，但不是 SQL 标准。

**常见转换对照：**

| 目标类型 | MySQL | PostgreSQL |
|---------|-------|-----------|
| 整数 | `CAST(x AS SIGNED)` | `x::INT` |
| 小数 | `CAST(x AS DECIMAL)` | `x::NUMERIC` |
| 字符串 | `CAST(x AS CHAR)` | `x::TEXT` 或 `x::VARCHAR` |
| 日期 | `CAST(x AS DATE)` | `x::DATE` |
| 时间戳 | `CAST(x AS DATETIME)` | `x::TIMESTAMPTZ` |
| JSON | — | `x::JSONB` |
| 向量 | — | `x::VECTOR(1536)` |

## 7. JSON 处理

### 7.1 存储原理

```
MySQL JSON                              PostgreSQL JSONB
──────────                              ────────────────
存储：原始文本                           存储：解析后的二进制
┌──────────────────────┐               ┌──────────────────────┐
│ {"name":"Tom","age":25} │            │ 二进制结构化数据        │
│  ↑ 每次查询需重新解析    │            │  ↑ 查询时直接访问       │
└──────────────────────┘               └──────────────────────┘
写入：快（直接存文本）                    写入：慢（需要解析+压缩）
查询：慢（每次解析）                      查询：快（索引支持）
```

### 7.2 路径表达式差异

```sql
-- 创建测试数据
-- MySQL
CREATE TABLE t (data JSON);
INSERT INTO t VALUES ('{"name": "Tom", "address": {"city": "Beijing"}, "tags": ["a","b"]}');

-- PostgreSQL
CREATE TABLE t (data JSONB);
INSERT INTO t VALUES ('{"name": "Tom", "address": {"city": "Beijing"}, "tags": ["a","b"]}');
```

```sql
-- 提取顶层字段
-- MySQL
SELECT data->'$.name' FROM t;        -- 返回 JSON: "Tom"（带引号）
SELECT data->>'$.name' FROM t;       -- 返回文本: Tom（不带引号）

-- PostgreSQL
SELECT data->'name' FROM t;          -- 返回 JSONB: "Tom"（带引号）
SELECT data->>'name' FROM t;         -- 返回文本: Tom（不带引号）

-- 提取嵌套字段
-- MySQL
SELECT data->'$.address.city' FROM t;      -- 用 $ 前缀的路径表达式
SELECT data->>'$.address.city' FROM t;

-- PostgreSQL
SELECT data->'address'->'city' FROM t;     -- 链式操作符
SELECT data->'address'->>'city' FROM t;
-- 或者使用 JSON Path（PG 12+）
SELECT data #>> '{address,city}' FROM t;
```

**原理：** MySQL 用 `$.key` 路径表达式（类似 JavaScript），PostgreSQL 用 `->` 链式操作符（类似函数调用链）。PostgreSQL 的方式更灵活，每步可以混合 `->` 和 `->>`。

### 7.3 JSON 查询与索引

```sql
-- MySQL：JSON 列上的虚拟列 + 索引
ALTER TABLE t ADD COLUMN name_text VARCHAR(50) 
    GENERATED ALWAYS AS (JSON_UNQUOTE(data->'$.name')) STORED;
CREATE INDEX idx_name ON t(name_text);

-- 或者函数索引（MySQL 8.0.13+）
CREATE INDEX idx_name ON t((CAST(data->>'$.name' AS CHAR(50))));

-- PostgreSQL：GIN 索引（原生支持）
CREATE INDEX idx_data_gin ON t USING GIN (data);             -- 通用 GIN
CREATE INDEX idx_data_path_gin ON t USING GIN (data jsonb_path_ops);  -- 更小的索引

-- PostgreSQL 特定路径索引
CREATE INDEX idx_data_name ON t ((data->>'name'));           -- 表达式索引
```

**原理：** PostgreSQL 的 GIN（Generalized Inverted Index）是倒排索引，为 JSONB 中每个键值对建立索引条目，查询时无需解析 JSON。MySQL 没有原生的 JSON 索引，需要通过虚拟列或函数索引间接实现。

### 7.4 JSON 包含查询

```sql
-- MySQL
SELECT * FROM t WHERE JSON_CONTAINS(data, '"Tom"', '$.name');
SELECT * FROM t WHERE JSON_CONTAINS(data, '{"name": "Tom"}');

-- PostgreSQL：使用 @> 操作符（更简洁）
SELECT * FROM t WHERE data @> '{"name": "Tom"}';

-- 数组包含
SELECT * FROM t WHERE data->'tags' ? 'a';              -- 包含某个元素
SELECT * FROM t WHERE data->'tags' ?| ARRAY['a','b'];   -- 包含任一元素
SELECT * FROM t WHERE data->'tags' ?& ARRAY['a','b'];   -- 包含所有元素
```

### 7.5 JSON 更新

```sql
-- MySQL
UPDATE t SET data = JSON_SET(data, '$.name', 'Jerry');
UPDATE t SET data = JSON_INSERT(data, '$.age', 30);     -- 键不存在时插入
UPDATE t SET data = JSON_REMOVE(data, '$.age');

-- PostgreSQL：使用 || 合并或 - 删除
UPDATE t SET data = data || '{"name": "Jerry"}'::JSONB;   -- 合并更新
UPDATE t SET data = data - 'age';                          -- 删除键
UPDATE t SET data = jsonb_set(data, '{address,city}', '"Shanghai"');  -- 深层更新
```

## 8. 模糊匹配与大小写

### 8.1 LIKE 行为差异

```sql
-- MySQL：LIKE 默认不区分大小写（取决于排序规则 collation）
SELECT * FROM users WHERE name LIKE '%tom%';   -- 能匹配 Tom, TOM, tom
-- 原理：MySQL 默认 collation 是 utf8mb4_general_ci（ci = case insensitive）

-- PostgreSQL：LIKE 区分大小写
SELECT * FROM users WHERE name LIKE '%tom%';   -- 只匹配 tom，不匹配 Tom
-- 原理：PostgreSQL 的 LIKE 逐字符比较，不涉及 collation

-- PostgreSQL：ILIKE 不区分大小写（PostgreSQL 特有）
SELECT * FROM users WHERE name ILIKE '%tom%';  -- 能匹配 Tom, TOM, tom

-- PostgreSQL：COLLATE 指定排序规则
SELECT * FROM users WHERE name LIKE '%tom%' COLLATE "zh-CN-x-icu";
```

### 8.2 正则匹配

```sql
-- MySQL
SELECT * FROM users WHERE name REGEXP '^[A-Z]';

-- PostgreSQL：使用 ~ 操作符
SELECT * FROM users WHERE name ~ '^[A-Z]';          -- 区分大小写
SELECT * FROM users WHERE name ~* '^[A-Z]';         -- 不区分大小写
SELECT * FROM users WHERE name !~ '^[A-Z]';         -- 不匹配
SELECT * FROM users WHERE name !~* '^[A-Z]';        -- 不匹配（不区分大小写）
```

**原理：** PostgreSQL 的正则直接使用 POSIX 正则表达式，比 MySQL 的 REGEXP 功能更强（支持 lookahead、lookbehind 等）。

## 9. UPSERT（冲突处理）

### 9.1 语法对比

```sql
-- MySQL：ON DUPLICATE KEY UPDATE
INSERT INTO users (id, name, email)
VALUES (1, 'Tom', 'tom@example.com')
ON DUPLICATE KEY UPDATE 
    name = VALUES(name),           -- VALUES() 引用插入值
    email = VALUES(email);

-- PostgreSQL：ON CONFLICT DO UPDATE
INSERT INTO users (id, name, email)
VALUES (1, 'Tom', 'tom@example.com')
ON CONFLICT (id) DO UPDATE SET     -- 指定冲突列（更精确）
    name = EXCLUDED.name,          -- EXCLUDED 引用插入值
    email = EXCLUDED.email;
```

### 9.2 原理差异

```
MySQL UPSERT 流程                       PostgreSQL UPSERT 流程
──────────────────                       ────────────────────
1. 尝试 INSERT                           1. 尝试 INSERT
2. 遇到唯一键冲突                         2. 遇到唯一约束冲突
3. 自动判断是哪个唯一键冲突               3. 只看 ON CONFLICT 指定的约束
4. 执行 UPDATE                            4. 执行 UPDATE（仅当指定约束冲突）
```

**关键区别：**
- PostgreSQL 需要显式指定冲突列/约束 `ON CONFLICT (id)`，MySQL 自动判断
- PostgreSQL 用 `EXCLUDED` 引用新值，MySQL 用 `VALUES()`
- PostgreSQL 支持部分冲突：`ON CONFLICT (id) WHERE is_active = TRUE`

```sql
-- PostgreSQL 支持 DO NOTHING（忽略冲突）
INSERT INTO users (id, name) VALUES (1, 'Tom')
ON CONFLICT (id) DO NOTHING;

-- MySQL 等价写法
INSERT IGNORE INTO users (id, name) VALUES (1, 'Tom');
```

```sql
-- PostgreSQL 支持指定约束名
INSERT INTO users (id, name) VALUES (1, 'Tom')
ON CONFLICT ON CONSTRAINT users_pkey DO UPDATE SET name = EXCLUDED.name;
```

## 10. 布尔类型

```sql
-- MySQL
CREATE TABLE t (is_active TINYINT(1) DEFAULT 1);
INSERT INTO t VALUES (1), (0), (2), (-1);   -- 都能插入，2 和 -1 也是 "true"
SELECT * FROM t WHERE is_active;             -- 语法错误！MySQL 不支持
SELECT * FROM t WHERE is_active = 1;         -- 正确

-- PostgreSQL
CREATE TABLE t (is_active BOOLEAN DEFAULT TRUE);
INSERT INTO t VALUES (TRUE), (FALSE);        -- 只能插 TRUE/FALSE
INSERT INTO t VALUES (1);                     -- 报错！类型不匹配
INSERT INTO t VALUES ('t'), ('f');            -- 可以，文本表示
SELECT * FROM t WHERE is_active;              -- 正确！PG 原生支持
SELECT * FROM t WHERE is_active IS TRUE;      -- 更严谨
SELECT * FROM t WHERE is_active IS NOT FALSE; -- 排除 NULL 和 FALSE
```

**原理：** MySQL 用整数模拟布尔，任何非零值都是"真"。PostgreSQL 有真正的 BOOLEAN 类型，只接受 TRUE/FALSE/NULL。

## 11. 全文搜索

### 11.1 基础语法

```sql
-- MySQL：MATCH AGAINST
CREATE FULLTEXT INDEX idx_content ON documents(content);
SELECT * FROM documents WHERE MATCH(content) AGAINST('PostgreSQL 索引');

-- PostgreSQL：TSVECTOR + TSQUERY
ALTER TABLE documents ADD COLUMN content_tsv TSVECTOR;
CREATE INDEX idx_content_tsv ON documents USING GIN (content_tsv);

-- 插入时自动生成 tsvector
INSERT INTO documents (content, content_tsv)
VALUES ('PostgreSQL 是一个强大的数据库', 
        TO_TSVECTOR('zh', 'PostgreSQL 是一个强大的数据库'));

-- 查询
SELECT * FROM documents 
WHERE content_tsv @@ TO_TSQUERY('zh', 'PostgreSQL & 数据库');
```

### 11.2 原理差异

```
MySQL 全文搜索                          PostgreSQL 全文搜索
────────────────                        ────────────────────
倒排索引（内置）                         TSVECTOR + GIN 索引
┌───────────────┐                      ┌───────────────────────┐
│ 词 → 文档ID列表 │                     │ 词元(lexeme) → 位置列表 │
│ PostgreSQL → 1,3│                     │ 'postgresql':1:3,5     │
│ 索引 → 1,2     │                     │ '索引':2:4             │
│ 数据库 → 1,2,3 │                     │ '数据库':3:6,8         │
└───────────────┘                      └───────────────────────┘
解析器：内置 n-gram                       解析器：可配置（zhparser 等）
分词：按 n-gram 切分                     分词：按语言规则切分
排序：按 TF-IDF                         排序：TS_RANK / TS_RANK_CD
```

**关键优势：** PostgreSQL 的全文搜索支持配置中文分词器（zhparser/jieba），比 MySQL 的 n-gram 分词更精确。

## 12. 锁与并发控制

### 12.1 锁类型

```sql
-- MySQL：LOCK TABLES（表级锁）
LOCK TABLES users READ, orders WRITE;
-- 操作 ...
UNLOCK TABLES;

-- PostgreSQL：LOCK TABLE（更细粒度）
LOCK TABLE users IN SHARE MODE;               -- 共享锁
LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE;  -- 行级排他
LOCK TABLE users IN ACCESS EXCLUSIVE MODE;     -- 排他锁（阻塞一切）

-- PostgreSQL： Advisory Lock（应用级锁）
SELECT pg_advisory_lock(12345);   -- 获取编号 12345 的咨询锁
SELECT pg_advisory_unlock(12345); -- 释放
-- 不会自动出现在 pg_locks 中，由应用控制
```

### 12.2 行锁差异

```sql
-- MySQL InnoDB：SELECT ... FOR UPDATE 锁行
BEGIN;
SELECT * FROM users WHERE id = 1 FOR UPDATE;  -- 加排他锁
-- 其他事务不能修改这行
COMMIT;

-- PostgreSQL：行为相同，但支持更多选项
BEGIN;
SELECT * FROM users WHERE id = 1 FOR UPDATE;       -- 排他锁（阻塞 UPDATE/DELETE）
SELECT * FROM users WHERE id = 1 FOR NO KEY UPDATE; -- 弱排他锁（允许关联外键查询）
SELECT * FROM users WHERE id = 1 FOR SHARE;         -- 共享锁（允许读，阻塞写）
SELECT * FROM users WHERE id = 1 FOR KEY SHARE;     -- 弱共享锁（仅阻塞 SELECT FOR UPDATE）
COMMIT;

-- PostgreSQL：跳过已锁定的行
SELECT * FROM users WHERE id = 1 FOR UPDATE SKIP LOCKED;  -- 跳过被锁的行
-- 适用于队列消费场景：多个消费者并发取任务
```

**原理：** PostgreSQL 实现了 4 种行锁强度等级，从强到弱：`FOR UPDATE > FOR NO KEY UPDATE > FOR SHARE > FOR KEY SHARE`。这来自于 MVCC 的多版本设计——不同操作需要不同强度的锁。

### 12.3 MVCC 导致的差异

```sql
-- MySQL：UPDATE 后旧数据被 Undo Log 覆盖
BEGIN;
UPDATE users SET name = 'Jerry' WHERE id = 1;
-- Undo Log 保存旧值
COMMIT;
-- 旧值被清理

-- PostgreSQL：UPDATE 创建新版本，旧版本仍在
BEGIN;
UPDATE users SET name = 'Jerry' WHERE id = 1;
-- 新 Tuple 写入，旧 Tuple 标记为已过期
COMMIT;
-- 旧 Tuple 仍在磁盘上，直到 VACUUM 清理
```

**迁移注意：** PostgreSQL 中大量 UPDATE 会产生大量死元组，导致表膨胀。解决方案：

```sql
-- 查看死元组数量
SELECT relname, n_dead_tup FROM pg_stat_user_tables;

-- 手动清理
VACUUM users;           -- 标记空间可重用（不回收磁盘空间）
VACUUM FULL users;      -- 回收磁盘空间（锁表！生产慎用）
-- 推荐用 pg_repack 扩展替代 VACUUM FULL（不锁表）

-- 配置自动清理
-- postgresql.conf
-- autovacuum = on
-- autovacuum_vacuum_scale_factor = 0.1  -- 10% 行变化后触发
```

## 13. 字符串拼接

```sql
-- MySQL
SELECT CONCAT(first_name, ' ', last_name);           -- 函数
SELECT CONCAT_WS(',', 'a', 'b', 'c');                -- 带分隔符：a,b,c
-- || 在 MySQL 默认是逻辑或
SELECT 'a' || 'b';                                    -- 结果：0（逻辑或）

-- PostgreSQL
SELECT first_name || ' ' || last_name;               -- 操作符
SELECT CONCAT(first_name, ' ', last_name);           -- 也支持函数
SELECT CONCAT_WS(',', 'a', 'b', 'c');                -- PG 9.1+ 支持
-- || 在 PG 是字符串拼接
SELECT 'a' || 'b';                                    -- 结果：'ab'
```

**原理：** `||` 在 SQL 标准中是字符串拼接操作符。MySQL 默认将其解释为逻辑或（`OR`），需要设置 `PIPES_AS_CONCAT` SQL 模式才能当作拼接。PostgreSQL 遵循 SQL 标准，`||` 就是拼接。

**NULL 处理差异：**

```sql
-- MySQL
SELECT CONCAT('Hello', NULL);     -- 结果：NULL（任一参数为 NULL 则结果为 NULL）

-- PostgreSQL
SELECT 'Hello' || NULL;           -- 结果：NULL（同 MySQL）
SELECT CONCAT('Hello', NULL);     -- 结果：'Hello'（CONCAT 忽略 NULL）
SELECT COALESCE(name, '') || '!' FROM users;  -- 推荐写法
```

## 14. 分页查询

### 14.1 基础分页

```sql
-- MySQL 和 PostgreSQL 通用写法
SELECT * FROM users ORDER BY id LIMIT 10 OFFSET 20;

-- MySQL 独有语法
SELECT * FROM users ORDER BY id LIMIT 20, 10;
--                        offset ↑   ↑ limit
```

### 14.2 深分页问题与解决方案

**原理：** `OFFSET 1000000` 需要数据库扫描并跳过前 100 万行，即使只返回 10 行。

```sql
-- 慢查询：深分页
SELECT * FROM messages ORDER BY id LIMIT 10 OFFSET 1000000;
-- 需要扫描 1000010 行

-- MySQL/PostgreSQL 通用优化：游标分页（Keyset Pagination）
-- 第一页
SELECT * FROM messages ORDER BY id LIMIT 10;

-- 下一页（假设上一页最后一条 id = 10）
SELECT * FROM messages WHERE id > 10 ORDER BY id LIMIT 10;
-- 只需扫描 10 行！

-- PostgreSQL 独有优化：WITH TIES（PG 13+）
SELECT * FROM messages ORDER BY created_at LIMIT 10 WITH TIES;
-- 如果第 10 条和第 11 条 created_at 相同，都返回（避免分页边界问题）
```

## 15. DDL 与元数据查询

### 15.1 查看表结构

```sql
-- MySQL
DESC users;
SHOW CREATE TABLE users;
SHOW TABLES;
SHOW DATABASES;

-- PostgreSQL
\d users;                           -- psql 元命令
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'users';
SELECT pg_get_tabledef('app.users'); -- PG 16+
\dt                                  -- 列出表
\l                                   -- 列出数据库
```

### 15.2 DDL 事务

```sql
-- MySQL：DDL 自动提交，不可回滚
BEGIN;
ALTER TABLE users ADD COLUMN phone VARCHAR(20);
-- 自动提交！无法回滚
ROLLBACK;  -- 无效，列已添加

-- PostgreSQL：DDL 支持事务，可回滚
BEGIN;
ALTER TABLE users ADD COLUMN phone VARCHAR(20);
ROLLBACK;  -- 列未添加！
```

**原理：** PostgreSQL 的 DDL 操作被实现为对系统目录表（pg_class、pg_attribute 等）的 DML 操作，因此天然支持事务。MySQL 的 DDL 通过 ALTER TABLE 复制整表实现，过程中自动提交。

**实际价值：** 可以在事务中执行多条 DDL，要么全部成功，要么全部回滚，保证 Schema 一致性。

```sql
-- PostgreSQL 安全迁移
BEGIN;
ALTER TABLE users ADD COLUMN phone VARCHAR(20);
ALTER TABLE users ADD CONSTRAINT uk_phone UNIQUE (phone);
CREATE INDEX idx_users_phone ON users(phone);
-- 全部成功才提交
COMMIT;
-- 任何一步失败，全部回滚
```
