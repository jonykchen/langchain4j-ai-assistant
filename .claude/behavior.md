# Claude 编码行为准则

减少常见 LLM 编码错误的指导原则。

**权衡：** 这些准则偏向谨慎而非速度。简单任务可灵活处理。

---

## 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

实施前：
- 明确陈述假设。如有不确定，提问。
- 存在多种解读时，全部呈现 —— 不要静默选择。
- 如有更简单方案，说明。必要时提出反对。
- 如有不清楚之处，停下来。指出困惑点。提问。

**项目适配：**
- Java/Spring Boot：遵循现有分层架构（controller/service/repository）
- Vue 3：遵循现有组件结构（components/views/stores）
- LangChain4j：参考 `patterns.md` 中的 AiService 模式

---

## 2. 简洁优先

**解决问题所需的最少代码。无推测性设计。**

- 不添加未被要求的功能
- 不为单次使用代码创建抽象
- 不添加未被请求的"灵活性"或"可配置性"
- 不为不可能发生的场景添加错误处理
- 如果写了 200 行但 50 行就够，重写

自问："资深工程师会说这太复杂吗？" 如果是，简化。

**项目适配：**
- 不要添加未被请求的 DTO 转换层
- 不要过度封装 LangChain4j 接口
- 前端组件保持简单，避免过早抽象

---

## 3. 精准修改

**只动必须动的。只清理自己的遗留。**

修改现有代码时：
- 不"改进"相邻代码、注释或格式
- 不重构没坏的东西
- 匹配现有风格，即使你会用不同方式
- 发现无关死代码时，提及它 —— 不删除它

修改产生孤立代码时：
- 移除你的修改导致的无用 import/变量/函数
- 不移除预先存在的死代码，除非被要求

**检验：** 每一行修改都应能追溯到用户请求。

**项目适配：**
- Java：保持现有命名风格（如 `ChatController` → `XxxController`）
- Vue：保持现有组件结构（`<script setup>` + TypeScript）
- 配置：遵循 Nacos 配置优先原则

---

## 4. 目标驱动执行

**定义成功标准。循环验证。**

将任务转化为可验证目标：
- "添加验证" → "为无效输入编写测试，然后使其通过"
- "修复 Bug" → "编写复现测试，然后使其通过"
- "重构 X" → "确保前后测试都通过"

多步骤任务，陈述简要计划：
```
1. [步骤] → 验证：[检查点]
2. [步骤] → 验证：[检查点]
3. [步骤] → 验证：[检查点]
```

强成功标准让你能独立循环。弱标准（"让它工作"）需要持续澄清。

**项目适配：**
- 后端修改：运行相关单元测试验证
- 前端修改：启动开发服务器验证功能
- API 变更：运行 `scripts\run-tests.bat e2e` 验证

---

**准则有效的标志：** diff 中更少的不必要修改，更少的过度复杂重写，澄清问题在实现前而非错误后出现。
